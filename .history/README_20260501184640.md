# Event Booking Platform — Backend API

This was built as part of a technical assessment. The task was to build an event discovery API where users can browse, search, and filter upcoming events. I focused on the backend side since that's my primary area.

---

## Stack

- **NestJS + TypeScript** — I went with NestJS because the structure it enforces (modules, controllers, services) maps well to what the assessment was looking for: clean separation of concerns and a logical folder layout. It also meant I could focus on the actual problem rather than setting up project conventions from scratch.
- **class-validator + class-transformer** — handles DTO validation and type coercion for query params.
- **JSON file for data** — both endpoints are read-only so a flat JSON file loaded at startup was enough. No database setup needed, nothing extra to configure.
- **Docker** — so it runs the same way everywhere without needing Node installed locally.

## Running the Project

### Option 1 — Docker (easiest)

You just need [Docker Desktop](https://www.docker.com/products/docker-desktop) installed.

```bash
git clone <your-repo-url>
cd event-backend
docker-compose up --build
```

### Option 2 — Local

```bash
git clone <your-repo-url>
cd event-backend
npm install
npm run start:dev
```

Either way, the API runs at `http://localhost:3000/api`.

The controller has no logic in it — it just receives the request and calls the service. All filtering, searching, and pagination happens in the service. That was a deliberate decision to keep things easy to test and easy to follow.

## API Reference

### GET /api/events

Returns a list of events. Without any query params it returns all 15 events paginated at 12 per page.

**Query Parameters**

| Parameter   | Type   | Required | Default | Description                                       |
|-------------|--------|----------|---------|---------------------------------------------------|
| `search`    | string | No       | —       | Matches against event name or venue name          |
| `category`  | string | No       | —       | One of: `Music`, `Tech`, `Food`, `Art`, `Fitness` |
| `date_from` | string | No       | —       | ISO date format e.g. `2026-05-01`                 |
| `date_to`   | string | No       | —       | ISO date format e.g. `2026-05-31`                 |
| `page`      | number | No       | `1`     | Which page of results to return                   |
| `limit`     | number | No       | `12`    | How many results per page                         |

**Example Requests**

```
GET /api/events
GET /api/events?search=jazz
GET /api/events?category=Tech
GET /api/events?date_from=2026-05-01&date_to=2026-05-31
GET /api/events?category=Music&page=1&limit=5
```

**Example Response**

```json
{
  "data": [
    {
      "id": "evt-001",
      "name": "Downtown Jazz Night",
      "category": "Music",
      "date": "2026-05-15T19:00:00Z",
```

### GET /api/events/:id

Returns a single event with full details including description, organizer info, and spots remaining.

```

```

Returns `404` if the event doesn't exist.

## How Pagination Works

Every response from `GET /api/events` includes a `meta` object alongside the data. Here is what each field means:

```json
"meta": {
  "total": 15,
  "page": 1,
  "limit": 5,
  "totalPages": 3
}
```

- **`total`** — the total number of events that matched your filters, not just what's on the current page. If you filtered by `category=Music` and 4 events matched, `total` will be `4` regardless of which page you're on.
- **`page`** — the page you're currently on.
- **`limit`** — how many events are returned per page.
- **`totalPages`** — calculated as `Math.ceil(total / limit)`. This tells you how many pages exist so you know when there's nothing left to fetch.

Walking through all 15 events with a limit of 5:

```
GET /api/events?page=1&limit=5
→ returns events 1-5,   meta: { total: 15, page: 1, limit: 5, totalPages: 3 }

GET /api/events?page=2&limit=5
→ returns events 6-10,  meta: { total: 15, page: 2, limit: 5, totalPages: 3 }

GET /api/events?page=3&limit=5
→ returns events 11-15, meta: { total: 15, page: 3, limit: 5, totalPages: 3 }
```

One thing worth noting — pagination always runs after filtering. So if you request `?category=Tech&page=1&limit=5`, the API first filters down to only Tech events, then paginates that result. The `total` in `meta` reflects the filtered count, not the full 15.

## Error Responses

All errors return the same shape:

```json
{
  "statusCode": 404,
  "message": "Event with id evt-999 not found",
  "path": "/api/events/evt-999",
  "timestamp": "2026-05-01T10:30:00.000Z"
}
```

| Status | When it happens                                                                 |
|--------|---------------------------------------------------------------------------------|
| `200`  | Everything worked                                                               |
| `400`  | Invalid query params — wrong category value, negative page number, bad date format |
| `404`  | Event id doesn't exist                                                          |
| `500`  | Something unexpected broke on the server side                                   |

## Trade-offs and What I'd Change

**JSON file instead of a real database** — works fine here because both endpoints are read-only and the dataset is small. With write endpoints or real users I'd switch to PostgreSQL with a proper seed script and migrations.

**No caching** — every request re-runs the filter and pagination logic over the array. For a read-heavy API like this, caching filtered results even briefly would make a noticeable difference at scale.

**No environment config** — the port and CORS origin are hardcoded in `main.ts`. In a real project those would live in a `.env` file using `@nestjs/config`.

**Swagger docs** — I'd add `@nestjs/swagger` so the API is self-documenting and testable from the browser without needing Postman.
